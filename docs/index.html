Local inference deployment guide for the M3 Ultra stack

A build brief for Claude Code. It condenses one long working session into rules, three concrete deployments, a diagnosis task, a benchmark protocol, and every open question that must be answered before the router is changed.

0How to use this guide

Work packages WP1–WP6 (including WP3b) are the build. Each has a goal, preconditions, commands, a verification receipt that proves the feature actually ran, and exit criteria. Section 11 is reference material for larger models that are not part of this build. Section 14 lists questions that the owner must answer; the owner's standing rule is that design disagreements are resolved before build work starts, so stop and ask rather than guess when a work package depends on one of them.

Scope boundary. Do not change the production router until WP5 has produced a comparison and the owner has chosen. WP1–WP3b stand up candidate backends on new ports; they do not replace anything.

1Operating rules for Claude Code

  1. Configured is not running. Every speculative or batching feature must be proven with the receipt listed in its work package (health payload widths, per-request acceptance, telemetry). A flag in a launch command proves nothing.
  2. Clean bench environment. Before any timing run: unload every other model server on the host, do one warm-up generation, interleave A/B runs with about 90 s cooldowns, record macOS version, engine version or commit, MLX version, checkpoint repo and revision.
  3. Correctness before speed. For each speculative configuration, compare greedy output against the same engine's non-speculative path. Differences beyond floating-point near-ties disqualify the configuration.
  4. Let engines calibrate on this Mac. Do not copy caps, depths or thresholds measured on M4 or M5 machines. Use mtplx tune, mlx-dspark's first-run calibration and --max-draft auto, and mlx-serve's learned round costs.
  5. Pin versions. All three engines move weekly. Record exact versions in a lockfile or README next to each launch script, and re-run the correctness check after any upgrade.
  6. Bind to localhost. mlx-serve binds 0.0.0.0 by default. Every backend in this guide must listen on 127.0.0.1 behind the router, or use an API key.
  7. Never enable --wired-limit in mlx-dspark, --mode dflash for the 35B-A3B, or a DFlash2 drafter in mlx-serve (reasons in the relevant sections).
  8. Report, do not smooth over. If a result contradicts this guide, record the measurement and flag it. Two of this guide's earlier claims were overturned by exactly that (section 13).

3Hardware model: bandwidth versus per-token overhead

Each generated token costs (a) reading the active weights from memory and (b) fixed per-step work: hundreds of kernel launches, expert routing and scattered expert reads, CPU–GPU synchronisation and sampling. Which one dominates decides what helps.

ConsequenceDense 27B (bandwidth-bound)35B-A3B (overhead-bound)
4-bit vs 8-bit speedReal trade: fewer bytes, faster decodeBarely matters; choose quant for quality (8-bit)
Speculation gainLarge: 2–4× published on mlx-dspark for Qwen3.8-27BSmall: 1.32× (mlx-dspark), ~1.34× (mlx-vlm MTP on M4 Max)
Batching gainRows share the whole weight readRows share only ~2.8B non-expert weights; 2.11× at B=8 (mlx-dspark baseline)
Bigger chip helps?Yes, via bandwidthLittle at batch 1

Memory facts that constrain co-hosting

  • GPU memory cap. macOS lets the GPU wire only part of unified memory by default (roughly three quarters, Unverified exact figure for 256 GB). Raising it uses sudo sysctl iogpu.wired_limit_mb=…; leave headroom for macOS.
  • KV cost per token. Qwen3.8-27B: 0.086 GB per 1k tokens measured by mlx-dspark (64 KB target KV + 20 KB drafter context), ~16 GB at 262k. Qwen3.6-35B-A3B: 10 full-attention layers × 2 KV heads × 256 dim in bf16 ≈ 20 KB/token, ~5.4 GB at 262k Estimate.
  • Co-residency. Models that generate simultaneously share one bandwidth pool; a dense model at 8-bit reads per token about as much as a 13B-active MoE at 4-bit. The 35B-A3B is the cheapest co-tenant because it reads little per token, but its prefill still contends for GPU compute.

The central question of the session: can an engine batch concurrent requests and speculate at the same time on Qwen's hybrid (Gated DeltaNet + attention) models? It is hard because each request accepts a different number of drafts per round, and the recurrent GDN state cannot be trimmed like a KV list; it has to be rebuilt per row.

Why the combination is worth less than it sounds. Batching and speculation both fill idle compute. vllm-metal measured batched MTP on Gemma 4 E4B at +20% output tok/s at concurrency 1 and +0% at 8. mlx-dspark measured batched speculation at 0.97× of batched baseline at B=4 on a dense 4B. The mlx-serve, MTPLX and Splash numbers show real gains, so measure rather than assume (WP5).

Splash was missing from the first revision of this matrix. It launched on 2026-09-17 and was not found because only engines named in the session were searched. Treat this matrix as a snapshot, not a census.

5WP1: Qwen3.6-35B-A3B on MTPLX

Goal. Two candidate backends on the same checkpoint family: a single-stream MTP server and the batched-MTP (mtp_batch) server for concurrent agents.

Preconditions

  • Checkpoints from the official catalog only: Youssofal/Qwen3.6-35B-A3B-MTPLX-Optimized-Speed (4-bit body, calibrated INT4 MTP heads) or …-Optimized-Balance (6-bit body). The non-FP16 builds are correct for M3.
  • Do not use third-party bundles with a sidecar attached (for example the lightning-mlx packs). MTPLX refuses sidecars that were not trained against the exact trunk.
  • For mtp_batch: install the mlx-lm commit from PR #1642 into the same environment. Released mlx-lm 0.31.3 lacks it and leaks a Metal buffer per token during long batched decode. uv sync can silently revert it.

Commands

# install
brew install youssofal/mtplx/mtplx          # or: python3 -m pip install mtplx

# mlx-lm fix for the batch lane (source checkout shown in MTPLX docs)
uv pip install --python .venv/bin/python --no-deps \
  "mlx-lm @ git+https://github.com/ml-explore/mlx-lm.git@985af30df768a6f4dd2d0c7969d1868ca5dc3e1a"
.venv/bin/python -c 'from mlx_lm.models.cache import ArraysCache; c=ArraysCache(1); assert hasattr(c, "_lp_advance") and hasattr(c, "_len_advance")'

# A. single-stream server: measure depth on this Mac first
mtplx tune --model Youssofal/Qwen3.6-35B-A3B-MTPLX-Optimized-Balance --retune
mtplx serve --model Youssofal/Qwen3.6-35B-A3B-MTPLX-Optimized-Balance \
  --profile sustained --max --port 8000 --no-stats-footer

# B. batched MTP server (full construction contract; every flag is required)
mtplx serve --model Youssofal/Qwen3.6-35B-A3B-MTPLX-Optimized-Speed --download \
  --scheduler-mode mtp_batch --batching-preset throughput --generation-mode mtp \
  --load-mtp --depth 1 --max-active-requests 8 --decode-batch-max 8 \
  --context-window 131072 --profile turbo --verify-strategy target_prefix \
  --verify-core stock --mtp-batch-numerics throughput --port 8010

Port check. MTPLX's app and CLI share one server; mtplx start attaches to a running model instead of loading a second copy. Confirm that two mtplx serve processes on different ports really are independent before relying on A and B side by side. Unverified

Batch lane behaviour

  • 1 request uses the solo MTP route; 2–3 requests seal into a B3 lane; 4–8 into a B8 lane. Each row keeps its own KV, GDN state, sampler and seed.
  • Numerics: throughput (default, fastest, bounded BF16 drift from solo), balanced, b1-exact (solo-exact, runs serially). Published: 349 aggregate tok/s for throughput and 260 for balanced on their workload; hardware not stated.
  • Rejected in the lane with HTTP 400: response_format, vision input, background requests, depth other than 1. Every request must satisfy prompt + max_tokens ≤ 131,072.

Verification receipt

# send at least 2 simultaneous requests, then:
curl -s http://127.0.0.1:8010/health | jq '.scheduler | {mode, active_lane,
  numerics: .mtp_batch_numerics, route: .mtp_batch_route_id,
  last_real_width: .telemetry.last_real_width,
  batch_histogram: .telemetry.batch_histogram,
  fixed_width_histogram: .telemetry.fixed_width_histogram}'
# pass: last_real_width between 2 and 8; histogram shows widths 3 and/or 8

Settings

  • Presence and frequency penalty stay at 0 for coding and agent work (0 is an exact no-op that preserves MTP exactness).
  • Warm-prefix session bank and SSD session cache are on by default; keep them.
  • Sampling: read the checkpoint's generation_config.json rather than copying Qwen3.8 values (temperature 1.0 contract) onto Qwen3.6.

Exit criteria

  1. Both servers answer /v1/chat/completions and /v1/messages.
  2. Receipt passes for B.
  3. Single-stream tok/s and depth recorded from mtplx tune.
  4. Greedy correctness check passes on A.

6WP2: Qwen3.6-35B-A3B on mlx-dspark

Goal. Two instances, because this engine cannot combine the two on hybrid models: one speculative (single stream), one batched baseline (swarm).

Draft model

  • Instance A needs a standalone drafter. DSpark on this target uses a separate 1.53B dense block-8 draft model, not an MTP head inside the checkpoint. mlx-dspark resolves it from the target's model name and downloads it on first run, so the launch command has no --drafter flag. The same drafter serves 4-bit and 8-bit targets.
  • Instance B needs none. --mode baseline does not speculate.
  • Cost. The drafter takes about 5.7 ms of each round against an 11.5 ms target step (M4 Pro), which is why the speedup on this MoE is modest. It adds a small amount of resident memory beside the target.
  • Pin it. The drafter's repo id is not recorded in this guide Unverified. On first launch, read the resolved drafter repo and revision from the startup log or the benchmark JSON, write both into the version notes next to the launch script, and pass it explicitly with --drafter afterwards so a registry change cannot swap it silently.

Published reference (M4 Pro, 4-bit target, mlx 0.32)

Commands

pip install mlx-dspark      # mlx >= 0.32.0 installed automatically

# A. single stream: confidence threshold must be passed explicitly; do not pin --max-draft
mlx-dspark serve --model mlx-community/Qwen3.6-35B-A3B-8bit \
  --confidence-threshold 0.3 --prefix-cache-slots 4 --port 8080

# B. swarm: batched baseline (hybrids batch only without speculation)
mlx-dspark serve --model mlx-community/Qwen3.6-35B-A3B-8bit \
  --mode baseline --max-batch 8 --prefix-cache-slots 8 --port 8081

# reproducible sweep on this Mac
mlx-dspark benchmark --model mlx-community/Qwen3.6-35B-A3B-8bit --trials 3 --json

8-bit versus 4-bit is unmeasured for this MoE. The project's general rule (8-bit gives the best ratio) failed on its other MoE (LFM2.5-8B-A1B was a net loss at 8-bit). The drafter resolves for any quant. Run the benchmark on both and let the owner choose; default to 8-bit for quality.

Settings

  • Leave --kv-bits off: slightly slower at 32k, and this model's KV is small.
  • Never pass --wired-limit: can hang macOS hard enough to need a power cycle; no measured speed gain.
  • Prefix caching: v0.10.1+ stable-boundary snapshots fix the Qwen3.6 turn-2 miss caused by the pre-filled <think> opener. Keep it on.
  • Agents: --no-thinking for tool loops unless reasoning is needed; the model otherwise thinks before every tool call.
  • Binds 127.0.0.1 by default; add --api-key only if exposed.

Verification receipt

Each response carries an x_mlx_dspark block: accept length, decode and end-to-end tok/s, TTFT, prefix-cache tokens. Pass for A: mean accept length and speedup in the same range as the reference table (chat near 1.0×, math clearly above). GET /machine reports this Mac's measured bandwidth and roofline.

Exit criteria

  1. Both instances healthy on 8080 and 8081.
  2. Resolved drafter repo and revision recorded in the version notes, and instance A relaunched with it pinned via --drafter.
  3. Benchmark JSON for 4-bit and 8-bit saved with device stamp.
  4. Correctness check on A passes.

7WP3: Qwen3.8-27B 4-bit on mlx-serve

Goal. A concurrent MTP backend for the dense 27B, where batched MTP has published gains.

Preconditions

  • macOS 26.2 or later; the bundled MLX targets that version.
  • A checkpoint with an MTP sidecar. Without one, mlx-serve only does prompt-lookup speculation. Grounded choice: Youssofal/Qwen3.8-27B-MTPLX-Optimized-Speed (4-bit dynamic, 20.4 GB, 23.6 GB peak; 96.0% top-1 agreement with bf16, KL 0.012); mlx-serve states it loads MTPLX-published artifacts unmodified. ddalcu/Qwen3.8-27B-MLX-Serve-4bit exists but its contents are Unverified. The owner's existing affine g64 4-bit pack probably has no MTP head.
  • A release after 26.9.3, or the workaround below.

Commands

brew tap ddalcu/mlx-serve https://github.com/ddalcu/mlx-serve
brew install mlx-serve

mlx-serve --model ~/.mlx-serve/models/Youssofal/Qwen3.8-27B-MTPLX-Optimized-Speed \
  --serve --host 127.0.0.1 --port 11234 \
  --max-concurrent 4 --metrics --prefix-cache-disk 20GB

# only if pinned to 26.9.3 (grouped-verify crash on concurrent sampled requests, #446)
MLX_SERVE_MTP_BATCH_CORR=0 mlx-serve ...

Published reference (M4 Max)

  • 4 MTP streams sharing one verify: 72 → 119 tok/s aggregate.
  • 4 streams at 28k context: 26 → 64 tok/s after the batched-KV copy fix.
  • Grouped verify per stream: 39 vs 20 tok/s (issue #446 reporter).
  • Group planner over legacy per-request MTP, 4 streams: +30% at 4k, +27% at 16k, +19% at 64k (PR #412, M5 Max, Flash-Next).

Settings

  • MTP depth: adaptive up to --mtp-depth 3 (default). PLD stays on; it gates itself off on novel content.
  • No DFlash2 drafter. On 26.9.4 a DFlash2 drafter on a Qwen3.8-27B target fails at the first draft step (#454); older builds silently fell back (#224). With a drafter loaded, concurrent requests switch to the MTP head anyway.
  • KV quantization: evidence conflicts (README: about −10% decode at 2–4k; latest release: 8-bit KV as fast as bf16 at long context). Leave off unless running long-context agents, then measure.
  • --max-concurrent 1 did not serialise MTP groups on 26.9.3; do not use it as an off switch.
  • Host defaults to 0.0.0.0; always pass --host 127.0.0.1.

Verification receipt

mlx-serve logs per-request acceptance rate, per-round average and runtime-gate state for every speculative request; --metrics exposes Prometheus metrics. Pass: at concurrency 4, logs show MTP active on all four streams and no GenerationFailed with temperature > 0.

Exit criteria

  1. MTP sidecar detected (log line or /v1/models capabilities).
  2. Concurrency-4 sampled run completes with zero HTTP 500s.
  3. Correctness check at temperature 0 passes.

8WP4: diagnose the DFlash2 4-bit acceptance anomaly

Observation (owner's box, mlx-dspark v0.19.0, --mode dflash, temperature 0, ~125 tokens). 4-bit affine g64 target: accept_len 1.488, 17.0–17.3 tok/s with speculation vs 17.6–18.0 without. 8-bit target: accept ~4.0 from a single short probe on a different basis; 22–31 tok/s.

Why it is anomalous. mlx-dspark's own published result for the same target and drafter: 4-bit accept 5.14 and 2.30× (M4 Pro); 8-bit accept 5.53 and 3.63×. An independent M5 Max run of the stock bf16 DFlash2 drafter on affine 4-bit g64 targets measured 1.84–1.87× with 88–89% per-draft acceptance. The owner's 4-bit dense baseline (17.6–18 tok/s) is also far below the M5 Max's 33.3 tok/s on the same pack format, so something is slowing the whole 4-bit path, not only the drafter. A quantization-aligned drafter would help little: the only published study found about +2% acceptance.

Steps, in order

  1. Clean environment per rule 2 (nothing else resident; the M5 Max author's first run was invalidated by 37 GB of co-resident models).
  2. Re-measure the 8-bit pack with the identical protocol as the 4-bit.
  3. Measure dense baselines for both packs directly with mlx_lm. If 4-bit dense stays below 8-bit dense, the fault is upstream of speculation.
  4. Check context depth: at 32k, fixed cap-7 configs on this 4-bit target dropped to 0.53–0.97×, cap 3 gave 1.48×. Use short prompts and --max-draft auto (v0.14.0+ prices depth).
  5. Diff the two packs: config.json, tokenizer hash, chat template, wrapper layout (language_model.model.layers vs model.layers).
  6. Dump hidden states at target_layer_ids [5, 19, 33, 47, 61] from both packs for one prompt; cosine similarity should exceed ~0.99. Never change those layer ids; the drafter was trained on them.
  7. Check greedy spec output is token-exact against dense on both packs (a GDN rollback bug would break this).
  8. Cross-check with the cfontes/qwen3.8-27b-mlx-dflash2 MLX implementation on the 4-bit pack. Splash (WP3b) is a second reference: it runs a DFlash 2 draft on a 4-bit Qwen3.8-27B target at the fastest published speeds, which further suggests the problem is specific to the mlx-dspark path on this box.
  9. Only then sweep caps.

Exit. A root cause, or a clean result that contradicts the published numbers; if the latter, write it up for upstream.

Workloads and metrics

  • Prompts: short (~1k tokens), agent-realistic (~32k), and replayed Hermes traces. Same prompt set for every config. Sampling at the agents' real settings, plus a temperature-0 run for correctness.
  • Include cached-replay TTFT at 32k (Splash's strongest published claim). Record per request: TTFT, decode tok/s, end-to-end seconds, tokens generated, HTTP status, engine telemetry (accept length, batch width).
  • Report per config and concurrency: p50/p95 TTFT, per-stream and aggregate tok/s, seconds to a correct answer (the decision metric; tok/s only explains it), error count.

Pre-committed decision rules

  1. Any config with a correctness failure or any HTTP 5xx under sampled concurrency is disqualified until fixed.
  2. Any batching or speculative config without its receipt (section 5, 6, 7) is reported as unproven, not as a result.
  3. Single-stream route: lowest median seconds-to-correct-answer at concurrency 1.
  4. Swarm route: highest aggregate tok/s at the owner's expected concurrency, subject to a p95 TTFT ceiling the owner sets before the run (section 14, question 2).
  5. Ties within 5% go to the engine already in the stack (lower change cost).
  6. A 4-bit-only engine (Splash) can win a route only if it passes the owner's quality check against the 8-bit reference; speed alone does not qualify it for eval or agent traffic.

10WP6: router integration

The existing FastAPI router dispatches by model alias and by image presence, because no MLX speculative drafter runs through a vision tower. That constraint still holds for every engine here.

Routing rules to implement after WP5

  1. Request contains an image or video part: mlx-vlm, no drafter.
  2. Request sets response_format: any backend except MTPLX mtp_batch (it returns 400).
  3. Prompt + max_tokens above 131,072 on the 35B-A3B: not MTPLX mtp_batch.
  4. Otherwise route by alias to the WP5 winner for single-stream or swarm traffic. Keep one fallback alias to the existing backend.
  5. If Splash wins both routes, rules 1–3 may collapse, because Splash accepts images and JSON Schema in the same batched speculative path. Do not remove the mlx-vlm route until image requests are verified on Splash on this Mac, and keep an 8-bit backend for eval traffic (Splash is 4-bit only).

    6. Downstream consequences to flag in the PR: health checks per backend (each exposes /health); separate process supervision per port; a failing grouped-verify round in mlx-serve takes down every request in that group, so the router should retry idempotent requests once on 5xx.

    14Unresolved questions (owner decides before build proceeds)

    1. Expected concurrency for Hermes. Typical and peak simultaneous requests. Decides whether the swarm route matters and which WP5 cells count.
    2. p95 TTFT ceiling for the swarm route. Needed before WP5 runs (decision rule 4).
    3. Quant for the 35B-A3B. 8-bit default for quality versus 4-bit/6-bit MTPLX packs; MTPLX packs are Speed (4-bit) and Balance (6-bit), so a like-for-like 8-bit comparison across engines is not available.
    4. Role of the M2 Ultra. Reserve it, or host one backend to avoid bandwidth contention. ds4 on M2 Ultra is Unverified.
    5. Does the 35B-A3B replace Qwen3.6-27B? Requires an eval on Hermes tasks, not a speed test.
    6. mlx-serve checkpoint. MTPLX Optimized-Speed pack or ddalcu/Qwen3.8-27B-MLX-Serve-4bit (contents unverified).
    7. Version pins. Whether #446 is in a tagged mlx-serve release; whether mlx-lm PR #1642 has been released.
    8. Two MTPLX servers side by side. Confirm A and B in WP1 run as independent processes.
    9. macOS version on the M3 Ultra. Splash needs 26.4+, mlx-serve 26.2+. An OS upgrade affects every backend on the host; schedule it before WP3 and WP3b.
    10. Is 4-bit acceptable for agent traffic? Splash offers no 8-bit option. If 8-bit is required for Hermes, Splash can only take the latency route.
